## F1 [closed]: no scenario pins the requirement's "in this repository"; a run looked up where the note's URL points meets every THEN
The requirement reads a note only when its run is "in this repository" (`redline/changes/note-run/specs/ledger/delta.md:4-7`), and design §4 asks for the run as `gh api repos/{owner}/{repo}/actions/runs/<id>` (`docs/design.md:334-336`). Those are gh's placeholders for the checkout's own repository. No THEN pins this. S2's only repository case is "its `html_url` isn't the note's `run:`, as when the note names another repository's run" (`redline/changes/note-run/specs/ledger/delta.md:18`), and that case holds only for that lookup. Suppose `push_run(url)` takes the owner and repo from the note's `run:`. It then asks the repository the note names. A fork's push run of the same commit (a fork has the same SHAs) gives the note's URL as its `html_url`, `push`, `main`, `.github/workflows/redline.yml` and the noted `head_sha`. Its `redline` job runs under the fork owner's settings and re-runs, not this repository's. No THEN of S1–S6 rules that out, and whether a test notices depends on how `FakeActions` keys the runs it registers. Add a case that reads `unconfirmed`: GitHub has the named run in another repository, every other field is as in S1, and its `html_url` is the note's `run:`. One way to meet it is to ask only `repos/{owner}/{repo}/actions/runs/<id>`, taking only the id's digits from the note. That also keeps the rest of the note's text, which anyone with `write` sets, out of the request.
Resolution: the requirement now asks for the run in the checkout's own repository, by its id alone (`redline/changes/note-run/specs/ledger/delta.md:6-7`). S2 reads `unconfirmed` for a note naming another repository's run that GitHub has there, with every field as in S1 and the note's `run:` as its `html_url` (`redline/changes/note-run/specs/ledger/delta.md:21-22`).

## F6 [closed]: rigor `standard` is too low: the change authenticates CI's evidence and changes a public API; raise it to `critical`
The change decides whether a note's `result: pass` came from CI's own run or from anyone with the `write` role (`redline/changes/note-run/proposal.md:7-11`, `docs/design.md:331-333`, `docs/design.md:1700-1708`). It does so by asking GitHub with a token given a new permission, which makes it an authentication check on where the evidence came from. It also changes the interface of a tool that other repositories install from a commit and build their workflow from (`README.md:15-22`, `README.md:46-51`):
- Every ledger rebuild (`redline ledger`, `check-ledger`, `check-close` and `ci pr`; `src/redline/cli.py:418-428`, `src/redline/cli.py:319-326`, `src/redline/ci.py:129`) now reads GitHub's Actions API, where today it reads git alone (`src/redline/ledger.py:43-56`).
- The committed `ledger.yaml` gains a fourth result.
- An adopting workflow without `actions: read` can't read its own notes.

§8 makes auth and public APIs critical (`docs/design.md:1732-1733`). Raise `Rigor:` to `critical` (`redline/changes/note-run/proposal.md:3`); a raise needs no claim (`docs/design.md:439-441`). For this change that adds the blind relabel at C. G1 already has its `Track:` line, and no `hold` test needs `reach`.
Resolution: the proposal now says `Rigor: critical` (`redline/changes/note-run/proposal.md:3`), with the blind relabel as O6 [C] (`redline/changes/note-run/steps.md:20`).

## F8 [closed]: any failing `break:` entry excuses a failed job, so a forged note still turns a failed run into `pass`, and S3 pins this
A note checks out when the `redline` job concluded `success` exactly when the note records no failure (`redline/changes/note-run/specs/ledger/delta.md:4-6`). A failure is `result: fail` or any `break:` entry `fail` (`redline/changes/note-run/proposal.md:24-27`, `docs/design.md:339-341`). S3 reads `result: pass` with a failing entry and the job's `failure` as `pass` (`redline/changes/note-run/specs/ledger/delta.md:30`). Nothing limits which entry that may be, or which note it is in. F3 asked for that clause. As a result, anyone who can push the ref can still forge `pass`:
- Take any failed push run, for instance a G merge whose suite failed, which CI notes `result: fail` (`src/redline/ci.py:136`). Rewrite its note as `result: pass` with `break: {X: fail}`, where X is any name. The note records a failure and the job's `failure` agrees, so every red or green read from it is `pass` (`src/redline/ledger.py:52-53`). That is O-NOTE1's own attack. CI writes a `break:` map only on an R merge (`src/redline/ci.py:138-143`, `docs/design.md:296-297`), keyed by exactly the change's hold scenarios (`src/redline/ci.py:142`, `src/redline/breaks.py:177`, `src/redline/breaks.py:232`). So no real note looks like this one.
- On a failed R merge, the same made-up entry, with every real entry set to `pass`, makes each hold scenario's break `pass`.
- In a change with only hold scenarios, take a failed R merge and write `result: fail` with every entry `pass`. The note records a failure and checks out. check-close reads only a hold scenario's break (`src/redline/close.py:56`), never the note's `result:` (`src/redline/ledger.py:54-56`).

The non-goal "nor which `break:` entry failed when one did" (`redline/changes/note-run/proposal.md:51-53`) doesn't cover these. In the first case no break ran at all. In none of the three does any failure remain to block the close.

The fix: count a failing entry as the note's failure only when it names a hold scenario whose break the ledger reads from that same note. Then any other note that says `result: pass` needs the job's `success`. Read a break as `pass` only from a note that says `result: pass`, or state the third case as a limit under O-NOTE2. Add each forgery to S3, reading `unconfirmed` or at least not `pass`.

Re-audit: the requirement now counts a failing entry only when it names a `hold` scenario whose break the ledger reads from that note. It fails a note whose map names any other scenario, and it reads every break as `fail` from a `result: fail` note (`redline/changes/note-run/specs/ledger/delta.md:6-9`). S3 pins forgeries 2 and 3 (`redline/changes/note-run/specs/ledger/delta.md:32`, `redline/changes/note-run/specs/ledger/delta.md:34`). Forgery 1 isn't pinned, so F8 stays open. Every case of S3 is on the R merge (`redline/changes/note-run/specs/ledger/delta.md:30`). There, the change's `hold` scenarios and those whose break the ledger reads from the note are the same set. So an implementation that counts a failing entry for any of the change's `hold` scenarios, the `held` set `rebuild` already has (`src/redline/ledger.py:90`), meets every THEN of S1–S7. That implementation also reads a forged note on a failed G merge, `result: pass` with `break: {H: fail}` for the change's own H, as `pass`: the job's `failure` agrees with a failure it counts. Add that case to S3, reading `unconfirmed`: a note on a merge the ledger reads no break from, such as a green's, that says `result: pass` with H's entry `fail` beside the job's `failure`.
Resolution: S3 now reads `unconfirmed` for a note on a green's merge, which the ledger reads no break from, that says `result: pass` with H's entry `fail` beside the job's `failure` (`redline/changes/note-run/specs/ledger/delta.md:33-34`). Forgery 2 is pinned at `redline/changes/note-run/specs/ledger/delta.md:32` and forgery 3 at `redline/changes/note-run/specs/ledger/delta.md:35`. Each forgery F8 names now reads `unconfirmed` or `fail`, and an implementation that counts a failing entry for any of the change's `hold` scenarios fails S3. What that THEN says of H's break in the green's case is F18.

## F9 [closed]: a 404 doesn't only mean GitHub lacks the run, so a reader that can't see the repository reads every note `unconfirmed`, reported as not matching its run
P13 takes `gh`'s 404 text as the sign of a run GitHub doesn't have (`redline/changes/note-run/specs/ledger/delta.md:79`). Also, the checkout's own repository is whatever `gh` makes of `{owner}/{repo}` from the remotes (`redline/changes/note-run/specs/ledger/delta.md:6-7`). In a clone whose only remote is a fork, that is the fork, which has none of the runs. The fix: add a premise that GitHub also answers 404 for a repository the token can't see. Then either make that an error before a run's 404 counts, for instance by reading `repos/{owner}/{repo}` once per rebuild, with a 404 there an error naming the repository `gh` resolved. Or say in check-close's `unconfirmed` line, and in §5, that the run may only be out of the reader's sight.
Resolution: the rebuild reads the checkout's own repository once, before any run, and a 404 there is an error naming that repository, with no run asked for (`redline/changes/note-run/specs/ledger/delta.md:10-13`, `redline/changes/note-run/specs/ledger/delta.md:49`). P13 states that GitHub answers that 404 for a repository it doesn't show the token (`redline/changes/note-run/specs/ledger/delta.md:87`), and §4 says why the repository is read (`docs/design.md:351-355`). That read doesn't cover the fork-only clone F9 also named, and that case isn't kept open. It needs the notes fetched into a clone whose `gh` resolves `{owner}/{repo}` to a fork, and it fails closed, since CI's check-ledger rejects the ledger that clone writes. What's left is a misleading line in that one local setup.
