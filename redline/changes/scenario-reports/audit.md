## F1 [waived]: red is a "body assertion failure", but no clause says what counts as an assertion, and an R test of code not yet written fails some other way
Waived-by: @Yusuprozimemet: fixed in b078595; audit stopped after round 1, unverified by the auditor
- PY.S1 and JS.S1 make only a body assertion failure red (`redline/changes/scenario-reports/specs/reports/delta.md:22`, `redline/changes/scenario-reports/specs/reports/delta.md:41-42`), and the design says "arbitrary exceptions" never are (`redline/changes/scenario-reports/design.md:63-65`). Today a `new` test is `xfail(strict=True)` with no `raises=` (`src/redline/plugin.py:37-39`), so any exception counts as its red. Jest's `test.failing` keeps nothing of what the body threw (`tests/toys/jest/node_modules/jest-circus/build/run.js:334-339`, the jest-circus the toy's lockfile installs, untracked). So for Jest the helper's rule is the whole definition, and no clause states that rule.
- An R step adds tests and nothing else (`specs/05-steps.md:23-24`, `redline/changes/scenario-reports/design.md:88`). A `new` test of code not yet written therefore raises `ImportError`, `AttributeError`, `NameError` or, in Jest, `TypeError`. `pytest.raises` with nothing raised, and `pytest.fail`, raise pytest's `Failed`. None of these is an `AssertionError`. Read literally, such a test is never red, and the consumer that takes "the first qualifying merged red" (`redline/changes/scenario-reports/design.md:21-23`) finds none for its scenario.
- Say which failures count for each runner, or make red any body failure with setup and teardown passing. Say how an R test of code that doesn't exist yet qualifies.

## F10 [deferred]: nothing bounds the report's size, and both note routes pass it through channels with size limits
Deferred-to: O-REPORT2, by @Yusuprozimemet
- The report holds an expected and an observed record for each linked instance (`redline/changes/scenario-reports/design.md:27-44`), so it grows with every change's tests. The direct route gives the note to git as one argument (`src/redline/ci.py:183-184`). The workflow hands it on base64, as a job output (`.github/workflows/redline.yml:65`, `.github/workflows/redline.yml:109`), and into the `note` job as one environment variable (`.github/workflows/redline.yml:131`).
- Linux won't start a process whose argument or environment string is over 128 KiB. Windows won't start one whose command line is over 32,767 characters. GitHub caps a job output at 1 MB. Past any of these limits no note is written. CI.S1 and CI.H2 assume the bytes arrive (`redline/changes/scenario-reports/specs/reports/delta.md:65`, `redline/changes/scenario-reports/specs/reports/delta.md:76`), and the design says no handoff change is needed (`redline/changes/scenario-reports/design.md:81-82`). Bound the report, or say what happens past a limit and give that a scenario.
