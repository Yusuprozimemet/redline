## 1. A commented-out or quoted marker counts as red, and as a link

**Where:** check-order and check-links read a marker as text on a line: `PYTEST` in
[runner.py:115](src/redline/runner.py#L115), used by `scan` ([order.py:28](src/redline/order.py#L28))
and `check_links` ([links.py:52](src/redline/links.py#L52)). The lock and check-break already read
decorators with Python's parser (`python_tests`, [runner.py:55](src/redline/runner.py#L55)), so the
two disagree.

**Reproduced:**
1. `redline/specs/greet/spec.md` declares `#### Scenario GREET.S1 [new]: greets`, and `greet.py`
   already returns `"hello"`.
2. R commit: `test_greet.py` has `# @pytest.mark.spec("GREET.S1", new=True)`, a comment, above
   `def test_greets(): assert greet() == "hello"`. The suite passes.
3. G1 commit: the real marker, `@pytest.mark.spec("GREET.S1")`.
4. `redline check-order` prints `ok GREET.S1: red <R> is an ancestor of green <G1>`, and
   `redline check-links` passes.

In CI the R merge's suite passes, so the ledger records red with `result: pass`, and check-close
accepts a scenario whose test never failed. A marker inside a string counts the same way:
`redline check-order` on Redline's own history reports `ID`, from the usage message in plugin.py,
and the scenarios of toy files held in test strings.

**Fix:** count a Python marker only where pytest does: in a decorator, found with `ast`. Keep
`git grep` to find the candidate files at each commit, then parse only those, cached by blob hash
since most files don't change between commits. Anchoring the pattern to a line-start `@` isn't
enough: Redline's own tests have 12 marker lines at line start inside triple-quoted strings. Jest
markers have the same problem, since `jest_tests` and the grep read comments and strings too;
`closing` in runner.py already skips both and can find the real `spec(` calls.

**Red test:** test_check_order: a commented `new=True` marker, and one inside a string, make no
red. test_check_links: such a scenario is unlinked.

**Design:** §4, where a test is linked to its scenario; §5, Runners ("A marker is read from one
line").

## 2. A PR sets what its own gates count

**Where:** `load_config` reads `redline/config.yaml` from the working tree
([config.py:24-27](src/redline/config.py#L24-L27)). check-lines leaves out files matching
`generated:` ([lines.py:38](src/redline/lines.py#L38)), and check-track exempts `generated:` and
`support:` files ([track.py:31](src/redline/track.py#L31)). Any PR may edit the config, in a step or
outside one.

**Reproduced:**
1. On main, `redline/config.yaml` has `generated: ["*.lock"]`.
2. A branch adds a 900-line `big.py` and changes `generated:` to `["*"]`.
3. `redline check-lines` prints `excluded big.py (generated)` and
   `ok: 0 changed lines since … (limit 400)`. With main's config the same diff gives
   `FAIL: 900 changed lines`.
4. `generated: "*.lock"`, a string instead of a list, does the same: `list("*.lock")` is
   `['*', '.', 'l', 'o', 'c', 'k']`, and `*` matches every path.

**Fix:** read `generated:` and `support:` at the merge-base with main, as check-track reads
`Track:` lines, "as the auditor saw it" (§5). Consider making a widened glob a claim, as a changed
`rigor:` is. In `load_config`, reject a `generated:`, `support:` or `rules:` entry that isn't a
list of strings.

**Red test:** test_check_lines: a PR that adds `generated: ["*"]` still counts its own lines, and a
string `generated:` is an error. test_track: a PR that widens `support:` doesn't exempt its own
files.

**Design:** §2 (invariant 3), §4 (`support:`), §5 (check-track), §7 (Approvals, if it becomes a
claim).

## 3. CI accepts a trailer naming a step that doesn't exist, or isn't next

**Where:** `pr_step` ([ci.py:65-77](src/redline/ci.py#L65-L77)) checks only that the trailer has a
`/`. `gates` ([pr.py:121](src/redline/pr.py#L121)) picks gates by comparing the step's name with
`S`, `R`, `G…` and `C`, so an unknown name gets the fewest gates, while the PR still counts as in a
step and may touch `redline/changes/`, `redline/contracts/` and `redline/specs/`. Only the local
`redline start` checks that a step exists and that the one before it merged.

**Reproduced** with a short script calling `ci_pr` and `gates`:
1. On main, change `add-greet` has steps S, R, G1 and C, and its S and R are merged. The living
   spec has `GREET.H0 [hold]` with `- THEN login fails` and a linked, passing test.
2. A branch changes that line to `- THEN login may succeed`, commits a ledger rebuilt with
   `redline ledger add-greet`, and carries `Redline-Step: add-greet/X`.
3. `ci_pr(repo, "main")` returns `("add-greet/X", [])`: no failures. The same diff gated as C fails
   check-specs. Without the trailer, CI refuses it for touching `redline/specs/`.

**Fix:** in `ci_pr`, before any gate, refuse unless the step is in the change's steps.md at the
merge-base and every step before it there is merged on main (`merged_steps`), as `start` refuses.
That also makes CI enforce invariant 1, the spec before the code: today CI doesn't check that a
G1 PR's S step is merged.

**Red test:** test_ci: a trailer naming a step steps.md lacks is refused, and so is a G1 PR whose S
isn't on main.

**Design:** §6 (start), §7 (what `redline ci pr` does).

## 4. A step can lower its own proposal's rigor

**Where:** `rigor_claim` ([pr.py:96](src/redline/pr.py#L96)) compares the config's `rigor:`, each
plan's `Rigor:` line and each plan's changes with the merge-base, but not proposals. `rigor`
([config.py:30](src/redline/config.py#L30)) reads the proposal from the working tree.

**Reproduced:**
1. On main, `redline/changes/add-2fa/proposal.md` has `Rigor: critical`. check-defects and
   check-relabel, as at C, report the missing `defects.md` and `relabel.yaml`.
2. A branch changes the line to `Rigor: lite`.
3. `rigor_claim` returns nothing, and the same two checks report nothing.

The level also decides whether every G step needs a `Track:` line, and whether the change's
initiative is critical, which is what asks for plan audits; lowering it drops those too. The lock
is safe: it checks every hash an entry has, whatever the level (§5).

**Fix:** in `rigor_claim`, compare each change's level at the merge-base (its proposal's `Rigor:`,
else the config's `rigor:`) with its level now. A difference needs `Redline-Rigor` and the
`redline:rigor` label, as the config's and a plan's lines do. A new proposal declares its level
without a claim, as a new plan does.

**Red test:** test_plan_rigor or test_pr: changing a proposal's `Rigor:` line after its S step needs
the claim, in `pr` and in `redline ci pr`.

**Design:** §4 (a change's level), §7 (the `Redline-Rigor` row), §8 ("never lower it").

## 5. mutmut can credit a break to the wrong tests, and the real `Mutator` is untested

**Where:** `Mutator.kills` ([breaks.py:37](src/redline/breaks.py#L37)) writes `paths_to_mutate`
and `pytest_add_cli_args = --redline-spec=<ID>` into the copy's `setup.cfg`
([breaks.py:44](src/redline/breaks.py#L44)).

**Evidence**, read from the mutmut 3.8.0 wheel's `mutmut/configuration.py` (not run: mutmut
doesn't run on Windows):
- `_config_reader` (lines 61–107) reads `[tool.mutmut]` from `pyproject.toml` when that table
  exists, and then never reads `setup.cfg`. In such a repository Redline's file list and
  `--redline-spec` filter are ignored: mutmut mutates what the repository's own settings name and
  runs its own test selection, so a mutant killed by any test counts as the scenario's break.
- `paths_to_mutate` is deprecated in favour of `source_paths` (lines 141–145).
- `also_copy` defaults to `tests/`, `test/`, `setup.cfg`, `pyproject.toml`, lockfiles and root
  `test*.py` (lines 184–195), so a hold test elsewhere may not reach the mutant run (not tried).

No test runs the real `Mutator`: every check-break test uses `FakeMutator`
([tests/test_check_break.py:40](tests/test_check_break.py#L40)). CI installs mutmut, but nothing
exercises it.

**Fix:** write Redline's settings where mutmut reads them: when the copy's `pyproject.toml` has
`[tool.mutmut]`, put them there, or remove that table from the copy. Use `source_paths`. Add the
hold tests' files, their `conftest.py` files and the `support:` files to `also_copy`. Then add a
test that runs the real `Mutator` on a toy repository, skipped where `Mutator.unavailable()` gives
a reason: a hold test that kills a mutant, one that kills none, and a repository with
`[tool.mutmut]`.

**Red test:** that test. It is skipped on Windows, so its red shows in CI (Linux), where mutmut is
installed.

**Design:** §5 (check-break, the `Mutator` seam).

## 6. A departure can't name a Jest test whose name has a space

**Where:** `CLAIM = re.compile(r"^(\S+) approved-by @\S+: \S")`
([lock.py:30](src/redline/lock.py#L30)), the only parser of the `Redline-Departure` trailer. A Jest
test is `path::name`, where the name is the string in `test("…")`, usually a sentence, and `\S+`
stops at its first space. On main since PR #34.

**Reproduced:** `CLAIM.match("greet.test.ts::returns nothing approved-by @maintainer: renamed")` is
`None`, while the pytest form matches. So `check_frozen` ([lock.py:113](src/redline/lock.py#L113))
reports such a test as changed "with no approved departure" whatever trailer the step carries:
once locked, it can't be edited at any step.

**Fix:** take the test as everything before the last ` approved-by @`:
`^(.+) approved-by @\S+: \S` (the greedy `.+` backtracks to the last match).

**Red test:** test_jest: a step edits a locked Jest test whose name has spaces (its `NAME` is
`greet.test.ts::returns nothing (or ")")`) with
`Redline-Departure: <test> approved-by @maintainer: <reason>`, and check-lock accepts it, noting
the label CI needs.

**Design:** §5 (departures). It belongs to build 5 part 7, or to a new O-ID that part owns.

## 7. `main` isn't protected, and the approval labels don't exist

**Evidence:** `gh api repos/{owner}/{repo}/branches/main/protection` answers 404, "Branch not
protected"; `gh api repos/{owner}/{repo}/rulesets` answers `[]`; `gh label list --search redline`
finds nothing.

**Why it matters:** §1 says the C step "can't merge without both" check-close and check-specs
([design.md:27](docs/design.md#L27)), and §7 makes CI the only evidence. Without a required status
check, a PR merges whether `redline` passes or not, and the push run only records `result: fail`
afterwards. None of the four claim labels (`redline:departure`, `redline:oversized`,
`redline:track`, `redline:rigor`) exists, so no claim can be approved.

**Fix (settings):** a ruleset on `main` that requires a pull request and the `redline` status
check, and blocks force pushes and deletion. Create the four labels. A required review needs a
second account, which item 8 provides.

**Design:** §7 should list the repository settings Redline's guarantees rest on, and the README
should repeat them as a setup checklist (item 16).

## 8. The agent can approve its own claims

**Why:** the agent runs `gh` with your credentials, so a label it applies counts as yours, an
admin's, and passes `approve` in [approval.py](src/redline/approval.py). §7 lists the limit
("Anyone holding a maintainer's token, including an agent given it, applies the label as that
maintainer"), and it holds for this repository today.

**Fix (settings):** give the agent its own GitHub account with the `write` role. It can still push
branches, open PRs and apply labels, but `role()` then returns `write`, which isn't in
`MAINTAINER`, so its labels approve nothing, with no code change. You are then not the author of
its PRs, so a ruleset can require your review before a merge, which is the maintainer's role in
§9.

## 9. PR runs get a token that can write the CI notes

**Where:** [.github/workflows/redline.yml:11-14](.github/workflows/redline.yml#L11-L14) sets
`contents: write` for the whole workflow, and its one job runs on both events. `actions/checkout`
keeps the token in `.git/config` by default (`persist-credentials: true`).

**Why it matters:** a PR's own code runs in that job: `pip install -e .`, its `conftest.py` and the
tests the agent wrote. For a branch in the same repository, which is how `redline pr` opens PRs,
the token has `contents: write`, so that code can `git push origin refs/notes/redline-ci` and
write `result: pass` or a `break:` map on any commit: the evidence §7 trusts. §7 says "The
workflow gives the push run the same read-only token as a PR run"
([design.md:993](docs/design.md#L993)); the token isn't read-only.

**Fix:**
- Permissions per job. The PR job gets `contents: read` (with `issues: read` and
  `pull-requests: read`), and its checkout sets `persist-credentials: false`.
- On a push, a read-only job runs the suite, check-break and the claims record, and passes the
  note's text on as a job output or an artifact. A second job with `contents: write` runs no
  repository code: it fetches the notes, adds that text to the merged commit and pushes.
  `redline ci push` needs a way to print the note instead of writing it.

**Red test:** the workflow tests ([test_ci.py:125](tests/test_ci.py#L125),
[test_claims.py:177](tests/test_claims.py#L177), [test_approval.py:68](tests/test_approval.py#L68))
read the YAML. Add: the PR job's `contents` permission is `read` and its checkout sets
`persist-credentials: false`; only the job that writes the note has `contents: write`, and it has
no `pip install`. [test_approval.py:72](tests/test_approval.py#L72) reads the workflow-level
`permissions`, which move into the jobs.

**Design:** §7 (correct the sentence, and describe the two push jobs).

## 10. A merged commit can miss its CI note

**Where:** `concurrency: group: redline-${{ github.ref }}` with `cancel-in-progress: false`
([redline.yml:16-18](.github/workflows/redline.yml#L16-L18)).

**Why it matters:** GitHub keeps at most one running and one pending run per group. When another
run queues, the pending one is cancelled, whatever `cancel-in-progress` says. After three merges
in quick succession the middle merged commit has no note, so its red, green or break stays
`unverified`, and check-close refuses ("waiting, not wrong") until someone notices and re-runs
that push run by hand.

**Fix:** drop the group for push runs, and make `Remote.push_notes`
([ci.py:46](src/redline/ci.py#L46)) retry. On a non-fast-forward rejection it fetches
`refs/notes/redline-ci`, merges it into the local notes (`git notes --ref=redline-ci merge -s ours`,
so this run's note wins on its own commit) and pushes again. Each run notes its own commit, so the
merge keeps every other run's note.

**Red test:** test_ci with `FakeRemote`: a push rejected once is fetched, merged and retried, and
the other run's note is kept. A workflow test: the push run has no shared concurrency group.

**Design:** §7.

## 11. Unpinned actions and toolchain, no CODEOWNERS, no LICENSE

- **Actions** are used by tag, `actions/checkout@v4` and `actions/setup-python@v5`
  ([redline.yml:24](.github/workflows/redline.yml#L24), [redline.yml:30](.github/workflows/redline.yml#L30)).
  The security auditor checks for "actions not pinned" (§4). Pin each to a commit SHA, with the
  tag in a comment.
- **The toolchain:** `pip install -e ".[mutation]"` resolves `pytest>=8` and `pyyaml>=6` afresh on
  every run. CI's runs are Redline's evidence, so a new pytest release can change what they say.
  Pin them with a constraints or lock file that CI installs from.
- **CODEOWNERS:** on `pull_request`, GitHub runs the workflow file from the PR itself, so a PR can
  change what its own CI runs, and Redline can't see that. A CODEOWNERS entry for `.github/` and
  `redline/config.yaml`, with code-owner review required, makes such a change a person's decision.
  It needs item 8's second account.
- **LICENSE:** the repository is public and `gh repo view` reports no license, so others have no
  right to use or modify it. Add one.

## 12. Text encoding on Windows

This machine's Python decodes text as cp1252 (`locale.getpreferredencoding(False)`, UTF-8 mode
off). Three failures, all reproduced:

1. **`config.yaml` is read without an encoding** ([config.py:24](src/redline/config.py#L24)). A
   rule containing "Ł" makes `redline start` end in
   `UnicodeDecodeError: 'charmap' codec can't decode byte 0x81`. `load_config` runs in check-lines,
   check-track and the brief, and in `rigor()` for any change whose proposal has no `Rigor:` line,
   so `pr` and most checks fail the same way. A "—" reads as mojibake, with no error.
2. **Printing a brief that contains "≤" crashes when stdout is a pipe or a file**
   (`UnicodeEncodeError: 'charmap' codec can't encode character '≤'`), which is how an agent
   session runs it. By then `start` has already recorded the open step.
3. **git's output is decoded as cp1252, and files as UTF-8.** `git()`
   ([order.py:25](src/redline/order.py#L25)) uses `text=True`. check-specs reads the living specs at
   the merge-base through `git show`, and now from the files, so an unchanged scenario containing
   "≤" was reported as
   `changed in redline/specs/x/spec.md since the merge-base, but no delta of add-y names it`. With
   `PYTHONUTF8=1` it passes. check-frozen compares the lock the same way, so a locked Jest test
   with a non-ASCII name would read as changed (not tried).

**Fix:** `encoding="utf-8"` in `git()`, in the other `subprocess.run` calls (pr.py, merged.py,
ci.py, breaks.py), in `load_config` and in the reads of the open-step file. At the top of `main()`,
`sys.stdout.reconfigure(encoding="utf-8", errors="replace")`, and the same for stderr. Add a
`windows-latest` job that runs the suite.

**Red test:** fixtures with non-ASCII text: a config rule with "Ł", a scenario with "≤" through
check-specs, and a brief printed through a subprocess pipe. They fail on Windows only, since CI's
Linux is UTF-8, which is another reason for the Windows job.

## 13. History scans are slow and repeated

**Evidence:** `redline check-order` took 8.1 s on this repository's 126 commits on Windows, with
nothing else running: about 64 ms a commit. The suite took 8 min 34 s for its 320 tests on
Windows, against about a minute in CI.

**Where:** `check_order` ([order.py:43](src/redline/order.py#L43)) calls `scan`, one `git grep` per
runner, on every commit of the history, even when given a window: the commits before it are still
scanned, as parents. `gates` runs check-order over the whole history, and at C, CI rebuilds the
ledger twice more (check-close and check-ledger each call `rebuild`, which calls `check_order`).
`merge()` in `rebuild` ([ledger.py:73-74](src/redline/ledger.py#L73-L74)) and the same search in
`claims` ([claims.py:113](src/redline/claims.py#L113)) call `is_ancestor` once per first-parent
commit until one contains the commit.

At this rate, a repository with a few thousand commits spends minutes per gate on Windows.

**Fix:**
- Scan only the commits that change a runner's files (`git log --format=%H -- <its paths>`) and
  carry each scenario's state forward through the rest, or read the marker changes from one
  `git log -p -G<pattern>`.
- Find the commit that merged a commit in one call: the oldest of
  `git rev-list --first-parent --ancestry-path <commit>..main`, or the commit itself when it is on
  the first-parent line.
- Within one run, compute check-order once and share it between check-order, check-close and
  check-ledger.

**Red test:** count the `git` calls (monkeypatch `redline.order.git`) for a history where one
commit of many touches a test, and assert the count doesn't grow with the history.

## 14. Open items without an owner are dropped silently; nothing checks steps.md

**Where:** `parse_steps` ([start.py:61](src/redline/start.py#L61)) keeps only lines matching
`- <ID> [<step>]: <text>` under `## Open items`, and ignores any other line.

**Reproduced:** under `## Open items`, `- rate-limit repeated wrong codes later` and
`- O2: no owner given` are both dropped without a word; only `- O3 [G1]: owned properly` is kept.

**Why it matters:** §1 promises "Every deferred item gets an ID and an owning step; CI fails on any
item without one" ([design.md:24](docs/design.md#L24)), and §2.7 says nothing is silent. Nothing
checks steps.md as a whole either: steps in the order S, R, G1…Gn, C; no step named twice; each
`Owns:` ID declared in the change's deltas; each `new` scenario owned by a G step. Today an
unowned `new` scenario is found only at C, by check-close.

**Fix:** a `check-steps <change>` gate, run by `pr` and `redline ci pr` at every step on the step's
change, failing on each of those.

**Red test:** a new test_steps.py: a malformed open item, a step out of order, an `Owns:` ID no
delta declares and a `new` scenario no G step owns each fail check-steps.

**Design:** §4 (steps.md), §6 (what `pr` runs).

## 15. Known limits without an O-ID or an owner

§2.7, and §12's own practice, give every open problem an ID and an owning step. These have
neither:

- §5, check-close ([design.md:846](docs/design.md#L846)): "What it doesn't prove: that the
  scenario's own test ran. A result is the whole suite's on the merged commit, and a test skipped
  there passes with it." Item 19 would close it.
- §12's first three bullets ([design.md:1154-1157](docs/design.md#L1154-L1157)): scenarios that
  can't be automated (§12 asks for "a recorded manual check with a reason", but there is no syntax
  for one, so check-links fails such a scenario and its change can't close); mutation cost on large
  codebases; and whether a test asserts its THEN clauses.

**Fix:** give each an O-ID and an owning build step, or say in §12 why it stays a judgment.

## 16. The README's status is out of date

[README.md:6](README.md#L6) says "steps 1–6 are on `main`". Step 5 isn't finished (part 7 isn't
merged), and step 7's parts 1–5 are. The README also has no install instructions, quickstart or
command list. A short walkthrough of one toy change from S to C, and item 7's settings as a
checklist, would let someone else try Redline.

## 17. Redline isn't run on itself

The repository has no `redline/specs/` or `redline/changes/`, and all its PRs are outside any step,
so `redline ci pr` gives them only check-lines, the rigor check, check-plan, check-helpers,
check-lock and the suite. The 12 marker lines in its tests are toy files inside strings. So its own
red before green is a commit-message convention, not checked evidence, although the README says
"Redline is built the way it asks others to work". Item 12's failures would have shown up on the
first `redline start` on this machine.

Also, the workflow's `pip install -e .` gates each PR with the Redline that PR contains, so a PR
that weakens a gate is checked by the weakened gate.

**Suggestion:** once item 12 is fixed, run Redline's next build steps through `redline start`,
`pr` and `merged`, with their own specs and markers, and install the gating Redline from main or
a release rather than from the PR.

## 18. Smaller code-quality items

- [cli.py](src/redline/cli.py): seventeen `run_*` functions repeat one try/print/return pattern,
  and `main` dispatches through an if-chain that falls through to check-order, so a new subcommand
  left out of the chain crashes on `args.rev`. `set_defaults(func=…)` on each subparser and one
  error wrapper would remove both. Only `Refused` and `RuntimeError` are caught, so a malformed
  YAML note or lock, or item 12's encoding errors, end in a traceback.
- [pr.py:67](src/redline/pr.py#L67) splits issue events on a literal tab character inside the
  string; an editor that turns tabs into spaces breaks label reading with no error. Use `"\t"`.
- About 70 imports between test modules (`from test_start import change  # noqa: F401`, …) share
  fixtures and toy builders. Fixtures belong in tests/conftest.py, and builders and constants in a
  plain helper module. The `noqa` comments go, and the modules stop depending on each other; they
  would break under pytest's `importlib` import mode.
- No linter or type checker. ruff and mypy (or pyright) in CI are cheap, given the type hints
  already there.
- `.gitignore` lists `.redline/session`, which nothing uses: the open step lives in the git
  directory.
- docs/design.md is 1,257 lines, and most of §12 is closed history. Moving closed O-items to a
  changelog, and splitting the document by topic, would let people and sessions read only what a
  step needs: the context bloat §1 names.

## 19. The bigger change: per-scenario outcomes from CI

Today a red, green or break result is the whole suite's result on the merged commit (§4, §5), and
which commit is red or green comes from marker text in git history. Item 1, item 15's first bullet
and the skip half of O-RUN4 all come from those two facts.

**Proposal:** the pytest plugin writes, for each test with a spec marker, its scenario, whether it
is `new`, and its outcome: failed strictly as expected (xfailed), passed, skipped, or not
collected. `redline ci push` stores that per scenario in the note. The ledger takes red from the
first merged commit where a scenario's `new` tests xfailed, and green from the first where its
tests passed without `new`, and check-close requires both. `redline ci pr` can then fail a PR in
which a locked hold test was skipped or not collected, which catches a skip added through
configuration, a `conftest.py` hook or a deselect, at every level. Jest's `--json` reporter gives
the same data for Jest tests (O-RUN1).

This changes the evidence model, so it belongs in the design first (§4 the ledger, §5
check-close, §7 the note), probably as a build step of its own.

## 20. Nothing measures token usage, so a change can run out mid-job

note-run S took three auditor runs of about 250k tokens each, plus a main session of about 140k,
and nothing showed it until the tokens were nearly gone.

**Proposal:** `redline cost <change>` reads Claude Code's local transcripts
(`~/.claude/projects/<project>/*.jsonl` and `<session>/subagents/`), whose replies carry `usage`
(input, cache read, output, thinking tokens), and prints a table per session and per agent run:
tokens, audit rounds per step, and the share used by the main session, the auditors and the
relabeller. A budget per change makes it warn when a step goes over. It only reports and warns:
the transcripts are local, not in CI, and editable, so it can't be a gate.

Ways to spend less, which the numbers should confirm: fewer audit rounds (check each fix the way
the auditor would before re-running it), a design.md index or per-section files so the auditor
reads less, a cap on finding length in the agent definitions, and one main session per audit
round.
